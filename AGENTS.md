# BarangAI project rules

- Follow the user's global AGENTS.md instructions.
- Build a barangay incident-reporting app. Since 3 Nov 2026 this is a standalone project, no longer tied to the PLDT AI in 30 Hours hackathon or the DLSU-D paper, so features may go beyond the paper. Each staff account belongs to one barangay; administrators see all. Staff and administrators use the same dashboard, differing only in that limit; staff decide deletion requests for their own barangay. Never auto-forward reports to outside offices.
- Required roles: resident, staff, administrator. Enforce permissions in the API.
- Keep model prediction, resident category, and staff-verified category distinct.
- Categories: flooding, fallen_trees, broken_streetlights, exposed_wiring, potholes, uncollected_garbage, damaged_signage, other. The model predicts only its trained subset.
- Required report path: Pending, Under Verification, Accepted, In Progress, Resolved; Under Verification may become Rejected, with a required reason from a fixed list. Every status change by staff or administrators needs a description, and residents see both; on a grouped case, every resident in it does, and "Already reported" is refused because rejection moves the whole case (3 Nov 2026). Residents see status history and staff `action` notes only: no staff IDs, coordination notes or automatic logs. AI hazard flags stay off the shared map (3 Nov 2026).
- Store private photographs outside public web roots. Strip metadata before storage.
- Use synthetic people and incidents in demos and tests. Never invent model metrics or user-study results.
- Keep external services optional in local tests. No paid API use or automatic billing.
- Do not commit, push, or deploy without the user's direct request or existing authorization in this chat. Commits are authored as the team member; commit messages, branch names and pull requests never name the tools used to write the code (no co-author or session lines).

## Decisions (26 Oct 2026)

- Hosting (changed 3 Nov 2026): runs locally. The laptop serves the site, API, SQLite database and private photos (`deploy/start-local.ps1 -Lan`); staff use its browser and residents use an Android app over the same Wi-Fi. The app is a Capacitor shell (`apps/mobile`) that loads the site from the laptop, keeping one origin and cookie auth, with native GPS because browsers refuse it on plain HTTP. Not a phone-only rewrite: reports must be shared between residents and staff. Render, Supabase and their files are parked, not in use.
- Auth: keep the app's own sessions (argon2, cookie + CSRF, Google OAuth). Not Supabase Auth. No email service: abuse is limited by database-counted caps (`usage.py`), and forgotten passwords are reset from the command line (3 Nov 2026).
- Frontend: Vite React SPA in feature folders, React Router, TanStack Query, Tailwind + shadcn/ui (guided by the `ui-ux-pro-max` skill). Not Next.js. Apple-like look: system font, blue accent matched to Kap's vest, warm neutrals, light/dark following the device with an in-app toggle. Residents use phones (bottom tabs, Home first, Android app); staff and admins use desktops (sidebar dashboard). UI changes need the user's approval of `visual-check` screenshots.
- Mascot Kap: 2D stills cut from the user's own pose sheet (salakot, vest recoloured blue), animated with CSS/Motion; never redrawn or regenerated. 3D is shelved (procedural Blender builds were rejected).
- Chatbot (3 Nov 2026, owner's decision, replacing keyword matching and curated topics): the model reads the resident's message and judges whether it is about the app, answering as Kap or returning a verdict that shows a fixed refusal. Emails, phone numbers and report IDs are masked first on a best-effort basis, report status stays database-only, and the privacy page says Cloudflare receives chat text.
- Motion: subtle and trustworthy (150–250 ms, bounce only on the map pin and success check), Motion library, CSS where enough, off under `prefers-reduced-motion`.
- Refactor order: fix, then redesign the frontend, then improve the backend. The old EfficientNet classifier (`inference.py`, `ml/`, `models/`) stays frozen and unused; `duplicates.py` stays frozen and is reused as is. The chatbot is in scope.
- Staff jurisdiction (2 Nov 2026): the server places each report in a barangay from its pin, using GeoJSON boundaries checked in plain Python (no PostGIS). Staff get a 404 outside their barangay; reports outside every boundary are for administrators only; a case stays in one barangay. Enforcement starts when the first barangay is loaded, so all staff share one desk until then. Not Supabase row policies: permissions stay in the API. Coverage (3 Nov 2026): the 75 barangays of Dasmariñas, using PSGC names and the NAMRIA/PSA shapes matched to them (`apps/api/data/dasmarinas-barangays.geojson`), chosen over OpenStreetMap as the more official source. The 13 barangays around DLSU Taft in Manila (`apps/api/data/taft-barangays.geojson`, same source, within about 250 m of the campus reading) were added on 3 Nov 2026 so demos work there too. Pins outside still submit, with a warning, and go to administrators.
- Report AI (option C, 28 Oct 2026): a Cloudflare Workers AI vision model (Mistral Small 3.1 24B; Gemma 3 is not allowed on the Workers Free account) writes the category, a description unique to each photo and hazard flags; MobileCLIP2-S0 (ONNX on Render, research-only licence: on 3 Nov 2026 the owner chose to keep it for now and review the terms) cross-checks the category, stands in when Cloudflare is down and gives duplicate embeddings. Location comes from the photo's GPS, then the phone's, with OpenStreetMap street names. When nothing looks broken, the AI still picks the closest category, marks it "AI unsure · please check" and says so in the description; checker-only and broken-streetlight guesses always ask the resident to check. Auto-fill only assists: residents review and edit all of it, and Review shows a disclaimer and a required tick whenever an AI or GPS value is still in use (1 Nov 2026); staff verify. Not SigLIP: Hugging Face Spaces with CPU are paid on the user's account. No local training data; tune and evaluate only with `apps/api/tools/evaluate_ai.py`, keeping tune and test photos apart. Face blurring uses YuNet (MIT, 3 Nov 2026), not the Haar cascade, which blurred wires and poles and missed tilted and small faces.
